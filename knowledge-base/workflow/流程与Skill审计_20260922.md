## 3. 按优先级列出的发现

### F01 · P1：没有跨游戏版本的原文差异检测

**证据**：旧 skill §3 要求更新零协、重建当前语料、合并旧补丁，然后运行 `scope.py`。`tools/scope.py:258` 只枚举当前 EN 文件；`:283` 至 `:298` 只比较当前英文和零协非空文本数量。没有旧游戏原文输入、源文哈希或批次版本清单。`--since` 在 `:303` 的分支与下一条判断重复，实际没有额外筛选作用。

**复现**：S02 将同一 id 的原文从 `Inflict 1 Burn.` 改为 `Inflict 2 Burn.`，零协仍写“施加1层烧伤”，工具报告“没有缺口”；S08 中有无 `--since` 输出完全相同。

**影响**：下一次更新改动已有技能数字、效果、剧情句子时，条数不变就可能被当成已覆盖。自动取最大零协版本也不能证明其译文已对应当前游戏。

**建议**：更新前保存官方 KR/EN/JP 原始文件快照和版本/哈希清单；更新后逐记录、逐字段比较新增、修改、删除、移动及结构变化。再核对零协覆盖与源文适用性。现有可覆盖写入的语料缓存不能替代只读版本快照。

### F02 · P1：范围工具既漏报，也把历史缺口误作新任务

**证据**：`scope.py:295` 只在 `base_n < en_n` 时进入细查；`:260` 不枚举韩文独有文件；`:287` 虽读取补丁数量，却不用于减去已覆盖内容。详细清单只处理 B 类（`:395` 附近），A/A0 未进入所谓“真正的工作清单”。

**复现**：S01 两侧同为两条文本、但零协缺少新 id，报告无缺口；S03 韩文独有新文件完全不扫描，并在 EN 文件数为0时报告无缺口；S04 已被补丁完整翻译的文件仍列为待补。

**真实数据纠正**：`StoryData/P10705.json` 的 EN、KR、零协均有36条记录。EN 每条额外带 `title`，KR 与中文示例没有此字段；旧“零协仅译36/72”的结论把字段数量当成剧情完成度。当前42条 B 类清单中，36条是该文件的 `title`，另4条是 `E003I3.title`，2条是历史补丁已补的 RPG 字段。不能据此断言有42句剧情漏译；是否应补标题需按目标结构与显示用途判断。

**建议**：分别输出“本次原文变化”“历史未覆盖”“源语言结构差异”“已由既有补丁处理”，并以最终有效汉化覆盖情况判断剩余工作。KR/EN/JP 文件集合取并集，源语言可用性细化到字段。

### F03 · P1：主验收器会放过缺字段及损坏的新增译文

**证据**：`verify_retrans.py:185` 附近以“零协存在该 id”豁免整条记录的英文检查；`:212` 附近只遍历中文已存在的字符串。标签仅检查 color/size/style/mark，且排序后比较；未检查引擎方括号标识符。`load()` 在 `:84` 捕获所有读取异常并返回空列表。

**复现**：V01 零协已有 id、正文字段为空时，补进去的中文丢失标签和 `{0}` 仍无错误；V02 中文删掉 `title` 仍无错误；V03 删除 `[Vibration]` 仍无错误；V04 将闭标签放到开标签前仍无错误；V05 缺官方源文件仍无错误；V06 无源文件且中文 JSON 损坏时仍返回0错误。

**影响**：“129文件、0错误”只能说明现有检查条件未触发，不能证明结构、标记和原文覆盖完整。`doctor.py` 可另查坏 JSON，但不能补上这些字段级盲区。

**建议**：读取错误显式失败；从预期目标结构出发，双向检查字段、类型、记录和嵌套数组。零协继承字段与本批次新增字段逐字段区分。检查引擎标记、占位符以及富文本合法嵌套；对语言结构差异建立明确映射，不简单要求全库中英文结构逐字相同。

### F04 · P1：合并工具承诺的回滚实际不可用

**证据**：`merge_zeroasso.py:239` 至 `:253` 写出4列：文件、合并字段路径、旧值、新值；`:204` 的回滚代码却解包5列。回滚只支持顶层字段，也没有解析嵌套路径或反转义换行。新增字段计数但不记录到 `changes`，而实际写盘受 `if changes` 控制（`:244`）。

**复现**：M01 执行正常合并后再 `--revert`，出现 `ValueError: ... expected 5, got 4`；M02 仅新增标题时，打印“采用1处、涉及0个文件、已写入”，磁盘却没有新字段。

**建议**：在恢复自动合并前，使用修改前完整文件备份及清单；或者实现带类型、稳定记录定位、完整字段路径与旧值前置条件的修改日志。必须通过“合并→回滚→逐文件哈希恢复”的测试。现有 `--revert` 不能承担恢复保障。

### F05 · P1：沿用旧补丁结构会遗漏新增记录、保留失效记录

**证据**：`merge_zeroasso.py:155` 起只遍历旧补丁记录；列表合并同样只遍历旧列表。合并字符串时没有排除 `model`、`speaker` 等结构标识符，与文字规则中的“不动定位字段”不一致。

**复现**：M04 新基准记录为 `[1,3]`、旧补丁为 `[1,2]`，合并后仍为 `[1,2]`；M03 `model` 和嵌套 `speaker` 字符串被替换。

**建议**：新批次从目标游戏所需结构和适用零协包构建；旧补丁仅提供候选译文。只在源文、记录身份和字段类型可验证时复用。对删除、改 id、结构迁移单独处理，不能继续执行“旧补丁结构永远正确”。

### F06 · P1：重复和空 id 在多处仍丢失，影响上下文证据

**证据**：`scope.py:195` 使用 `setdefault(id, record)` 保留首条并跳过空 id；`ctx_dump.py:46` 使用字典保留最后一条，输出时按同一 id 取原文（`:126`）；`align_index.py:33` 的 `(文件,id,字段)` 键覆盖同语言前值。旧 skill §4.3 又要求同 id 一起改，却没有证明它们一定是同一语义记录。

**复现**：S07 第二条重复 id 漏译和空 id 漏译均不进入清单；C01 两条同键韩文语料只剩后一条。

**建议**：采用保留重复项的记录表示；将 id 类型、重复出现序号、结构路径和上下文信息纳入定位。跨版本遇到空 id 或无法唯一对齐时列为人工确认项，不能退化成“取第一条”或无条件整表下标对齐。

### F07 · P1：语义修订规则与验收红线直接冲突

**证据**：`workflow/重译手册.md §0.6b` 明确要求合并后补回零协相对韩文少说的内容；旧 skill §3 第6步重申语义复核，但第7步又要求零协所有既有非空译文不变。`verify_retrans.py:redline_check` 会拦下这种修订，下次合并还会覆盖它。

**影响**：同一条改动按语义规则必须做，按验收规则又必须回滚，操作员无法同时满足。

**建议**：针对用户当前的“更新缺口补充”目标，本轮只编辑本批次确认需要翻译的字段；零协既有译文的语义疑点进入独立审计清单。若另行开展修订，应建立明确的例外范围与版本记录，而不是隐含混入补缺口流程。本次未擅自修改历史译文。

### F08 · P2：无活动批次、未扫描、通过三种状态混在一起

**实测**：归档后 `verify_retrans.py --all` 正确以退出码2拒绝空目标；`verify_output.py` 却仍输出“0文件、0问题”，退出码0。指定 `StoryData/S1004B.json` 时，它报“未生成”仍退出0。该工具固定读已被清理的 `out/LLC_zh-CN`（`:35`），与上一轮修改 `patch_v2` 的流程不一致。`check_speech_context.py` 扫描0句也退出0。D01 证明 `doctor.py` 在缺活动目录时仍可报“0文件 JSON 合法、环境就绪”。

**建议**：引入“等待更新／活动批次／已归档”状态。等待更新不是验收失败，也不是验收通过；没有批次时跳过产品验收并明确标注“不适用”。活动批次中目标缺失、扫描数量不足、读取失败应返回非零。所有工具显式接收同一个批次目录及预期目标清单。

### F09 · P2：范围查询会覆盖清单，清单又可能在无缺口时过期

**证据**：`scope.py:229` 为 `--save` 设置 `default=True`，没有关闭写入的参数；`:423` 附近只在 `scope` 非空时更新报告。

**复现**：S05 普通扫描即写出报告；S06 上次有缺口、下一次已无缺口时，旧报告仍保留。当前对话首次了解项目时的扫描也因此刷新了两份清单，而非纯只读。

**建议**：默认只读，显式 `--save` 才保存；报告带源快照、零协版本、扫描时间、覆盖范围与状态，即使零缺口也生成空的当次结果。历史报告按批次保存，避免成为下一轮误用的任务清单。

### F10 · P2：skill 将多种任务与发布动作绑在一起，迁移兼容性未处理

**证据**：旧 skill 触发范围包括查术语、验证、翻译、安装、发布，但统一完成条件要求游戏同步、推送仓库和制作发布包；没有按当前请求选择执行模式。发布示例含 `git add -A`、只增不删的复制和删除全部旧 ZIP 的命令；前者可能带入无关修改，后者可能留下失效文件或丢失历史版本。工作目录 `_kb` 不是仓库，旧第3步在该目录调用 `git diff --stat` 也不能验证补丁修改。

此外，skill 写死本机路径；以本机 Codex 的 `quick_validate.py` 检查，`whenToUse` 是不支持的 frontmatter 字段。这只证明**不能原样通过该 Codex 校验器**，不证明 DSH 不支持它，也不等于已完成 Codex 安装。

**建议**：区分查询、等待更新、范围核对、翻译、审校、安装、发布；完成条件随请求变化。发布使用本批次文件清单和暂存发布目录，保留历史包；是否安装或推送依据本次任务授权。若迁移到 Codex，再按目标格式调整发现位置和 frontmatter。本次只增加状态提示，没有迁移或改写原 skill 全文。

## 4. 文档中的次要误导

- “Python 3.14 陷阱”实际是 int 与 str 键不同的普通类型行为，不是该版本引入；应要求定位类型一致。
- `pm_lib.py build` 本身调用 `build_index(force=True)`，旧 skill 的“必须先删 `_file_index.json`”并非该命令的必要条件。
- “CN 行数与 KR 相近”不能证明对齐正确；语言独有字段、上游翻译进度和抽取规则都会改变计数。
- 主索引仍混有旧品牌拉丁原文规则、旧 TSV 产物路径和上一轮规模。状态提示已阻止把它们当作当前任务，但这些历史内容尚未逐项整理。
- `scope.py` 不统一 `LIMBUS_BASE_PACK` 的含义：其他若干工具接收工作区下的包名，它却直接返回环境变量作为语言目录。新版工具需统一路径解析和存在性检查。
- `workflow/更新与排障.md` 调用的 `check_schema.py` 当前不存在，并用 shell 回退信息掩盖失败；应移除过时调用或补齐真实结构校验。

## 5. 建议采用的下一轮流程

1. **等待更新**：冻结当前官方 KR/EN/JP、对应零协包及版本/哈希信息；无活动修改目录。历史补丁保持归档。注意：本次只归档了补丁及审计材料，尚未建立官方原文版本快照。
2. **发现更新**：保存新版原文快照；先比较新旧原文，而不是先合并旧补丁。零协尚未更新时，也能用旧包作术语参考，不能因此阻塞新内容翻译。
3. **确定范围**：分列本次新增、变更、删除、结构变动、旧译是否适用、零协已覆盖、历史缺口及待人工对齐项。字段非空本身不能证明旧译仍有效。
4. **创建新批次**：只在范围确定后建立新的工作目录。记录源语言、版本和每条译文依据；按目标结构生成覆盖文件，只编辑本批次允许的字段。
5. **翻译与审校**：保留现有术语和角色资料；先通读上下文，再译，再分语义与文风两轮检查。语义脚本仅作线索。
6. **验收与交付**：覆盖率、字段结构、标签、占位符、允许修改范围、源文时效、最终文件清单分别检查。按请求进行本地交付、安装或发布，不将它们视为同一个默认动作。
7. **完成与归档**：保存批次、证据、验收结果和恢复点，回到“等待更新”。归档中的旧文件不自动进入下一批次。

## 6. 修复顺序与完成标准

| 顺序 | 工作 | 可验收结果 |
| --- | --- | --- |
| 1 | 版本快照、批次状态、范围检测 | 同 id 改数字可发现；KR 独有内容可发现；历史缺口不会冒充本次更新 |
| 2 | 记录定位、结构与字段级验收 | 重复/空 id 不丢；缺字段和标记问题可报；零协留空处新译必须受检 |
| 3 | 重建或替换旧合并器 | 新增/删除按目标结构处理；结构标识符受保护；回滚恢复到原始哈希 |
| 4 | 重写 skill 主流程和文档入口 | 等待时不创建修改源；查询不触发发布；步骤能使用同一批次目录完整跑通 |

验收应覆盖本报告样例，并增加贴近真实 RPG 与 StoryData 结构的样本。通过这些机械测试仍不能代替韩文语义精读或游戏加载验证。
