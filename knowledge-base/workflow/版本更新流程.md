# 游戏版本更新流程

适用于“当前游戏与汉化处于基线版本，等待游戏更新，然后只处理本次变化”。`project.json` 是状态依据；没有活动批次时，不存在修改源。版本名由实际快照命名，不把示例 v1.0/v1.1 当真实游戏版本。

## 1. 等待更新：只保存基线

本项目已经保存 `snapshots/baseline_20260922/`，内含官方 KR/EN/JP 与零协文本的原始 JSON、逐文件 SHA-256、零协版本和 Steam build ID。原文快照不是翻译目录。

```bash
python3 tools/doctor.py
python3 tools/batch.py status
python3 tools/snapshot.py verify snapshots/baseline_20260922
```

首次建立另一个独立项目时，才运行：

```bash
python3 tools/snapshot.py capture --name baseline_<实际构建标识> --set-baseline
```

`--game-root` 可指定游戏根目录；`--base` 接受零协包根目录或 `LLC_zh-CN` 目录。未提供时自动发现零协包，但“版本号最大”仅用于选择候选，不代表已与游戏兼容。快照记录实际选中的包，后续批次不随工作区最新包漂移。显示版本未知时留空，只记录可读取的 Steam build ID。

快照不覆盖同名目录；每次使用都会校验完整文件集合与哈希。`doctor --quick` 只查清单，不进行全量哈希检查。

## 2. 游戏更新后：先保存新原文，再比较

零协尚未更新时，也能保存当前可用包作术语参考，不必等待它才能检测新内容。

```bash
python3 tools/snapshot.py capture --name update_<新的构建标识>
python3 tools/scope.py --new snapshots/update_<新的构建标识> --save out/update_scope.json
```

`--old` 不填时采用 `project.json` 的基线。没有 `--new` 时只报告等待状态；不创建文件。没有 `--save` 时扫描只读；显式保存时，即使零变化也更新本次报告，不能沿用旧待办。

报告包括：

- `files`：本次各语言的新增、修改、删除、移动及结构变化；同一 id 改数字也会出现。
- `history`：此前已经存在、当前零协仍未覆盖的字段，不自动进入本轮。
- `language_differences`：例如英文比韩文多 `title`；不是剧情漏译结论。
- `coverage`：`needs_translation`、`upstream_review`、`inherited`、`historical_gap`、`manual_alignment`。

非空的上游译文只说明“有候选”，不能证明已经适配改变后的原文。原文没有变化且唯一对齐的译文才默认复用。文件列表取 KR/EN/JP 并集，首选有内容的 KR，其次 EN、JP；默认结构采用该语言。目标结构内每个可唯一对齐的字段再按 KR→EN→JP 选择非空语义来源，并在批次中逐字段记录；歧义记录不自动跨语言借用。

若某字段应使用另一语言或需要特别结构适配，先核对实际引擎要求。工具不会按文本数量推断漏译；不能直接混加不同语言的字段。

## 3. 审核范围并建立本轮批次

```bash
python3 tools/batch.py create --name <批次名> --report out/update_scope.json --decisions out/update_decisions.json
```

简单的唯一 id 文本修改可省略 `--decisions`。报告绑定快照清单哈希，过期或手改报告会被拒绝。零变化不会创建批次。

决策文件是按相对文件名索引的 JSON 对象，例如：

```json
{
  "StoryData/Example.json": {
    "action": "translate",
    "structure_reviewed": true,
    "reason": "已核对本次新增记录及字段结构，采用韩文结构"
  },
  "StoryData/ReferenceOnly.json": {
    "action": "exclude",
    "reason": "只有英文改写；韩文与适用中文未变，已核对语义"
  },
  "Obsolete.json": {
    "action": "retire",
    "reason": "所有官方语言均已删除此文件"
  }
}
```

其他可用决策：

| 字段 | 用途 |
| --- | --- |
| `schema_language` | 显式选择 `kr` / `en` / `jp` 的目标结构；每字段语义仍优先可唯一对齐的 KR，不随意混加字段 |
| `alignment_reviewed` | 已人工检查重复/空 id；仍按完整路径分别翻译，不自动配对上游 |
| `include_history` | 同一个覆盖文件内的历史缺口经明确判断也须补齐；附原因，不扩展到其他文件 |
| `display_brackets` | 显式列出显示用单词，如 `Heathcliff`；其余拉丁方括号按引擎标记保留 |
| `action: upstream` | 人工确认上游已适配本次原文；必须附原因，新增/变更字段另需 `semantic_reviewed` 与 `style_reviewed`，仍检查标记 |

结构变化、只有参考语言变化、重复/空 id 会要求对应判断，工具不会把“第一条同 id”作为默认答案。这里的审核是译者基于证据填写的记录，不是要求用户每一步重复批准。

批次目录为 `batches/<批次名>/`，包含 `patch/`、受保护 `template/`、`scope.json`、`batch.json` 与 `transactions/`。这时才有修改源。目标结构来自新快照，删除的旧记录不从旧补丁带入。已有效继承的零协字段不可顺手润色。

## 4. 通读上下文、翻译和两轮审校

```bash
python3 tools/ctx_dump.py StoryData/Example.json --out out/context.txt
python3 tools/rpg_dump.py RPGSystem/Example.json --out out/rpg_context.txt
```

每种语言独立保留原始顺序、说话人、重复/空 id 和完整字段路径，避免伪对齐。译者先通读对话回合，再逐字段落笔。口吻、术语参考零协；语义以本批次实际源文为准，KR优先。仅有EN/JP时在批次中记录来源。

术语查询：当前版本零协实证优先，其次 `confirmed_pairs.tsv`、`glossary_all.clean.tsv`、人工分类表；旧表与当前原始证据冲突时采用已核实的当前证据并记下原因。角色文风查 `style/`，机制句式查 `style/机制句式模板.md`。零协既有译文的历史语义疑点单独记录，不混入本轮补译。

编辑清单是 JSON 数组，字段路径来自 `batch.json`，不从 `pos` 推测 id：

```json
[
  {
    "file": "StoryData/Example.json",
    "path": ["dataList", 0, "content"],
    "expected": "这里必须与当前字段原值逐字符相同",
    "text": "译文",
    "reason": "结合前后对话核对韩文指代与称呼，完成语义和文风两轮检查",
    "semantic_review": true,
    "style_review": true
  }
]
```

两项审校只在实际完成后填 `true`；初译可先填 `false`，再提交原值等于当前译文的同文编辑更新审校记录。没有改文字也允许记录审校，但不能把脚本通过当成语义已看过。

```bash
python3 tools/batch.py apply --edits out/edits.json --dry-run
python3 tools/batch.py apply --edits out/edits.json
```

只允许修改清单中的文本字段。旧值不符、重复编辑、类型变化、标记丢失会中止；不静默跳过。每次实际写入产生事务号，修改前保存完整文件和批次元数据，支持嵌套字段、真换行和制表符的字节级恢复。

```bash
python3 tools/batch.py rollback --transaction <事务号>
```

按逆序回滚；若有后续外部修改则拒绝覆盖。中断事务会阻止继续编辑，先用上述命令恢复。旧 `merge_zeroasso.py` 不再自动合并；仅作为同一显式编辑/回滚机制的兼容入口，默认只预览。

## 5. 验收与可选线索

```bash
python3 tools/batch.py verify
python3 tools/verify_retrans.py --all
python3 tools/verify_output.py --all
```

三个入口使用同一批次：核对源快照哈希、预期文件集合、模板完整性、字段类型、数组顺序、受保护值、标记与占位符以及当前译文绑定的审校记录。缺源、坏 JSON、无活动批次返回非零；等待状态下验收“不适用”，不应创建空目录强行通过。

可用 `--batch <目录>` 检查指定活动批次。显式源/译文比较仅检查结构与标记：

```bash
python3 tools/qa_check.py source.json translation.json
```

人工复核线索（默认只读）：

```bash
python3 tools/check_speech_context.py
python3 tools/sem_check.py --top 40
python3 tools/polish_scan.py --only StoryData --top 40
python3 tools/check_established_terms.py --top 40
```

筛子只检查当前批次字段，不替代语义判断；零疑点不是质量证明。无可识别角色台词时口吻工具明确标“不适用”。若需保存筛子报告，显式指定 `--save <报告.json>`。

## 6. 本地交付与结束

```bash
python3 tools/batch.py export --out out/delivery_<批次名>
```

输出目录必须不存在；只输出验收通过的本批次文件及 `delivery.json`（哈希、源快照、删除/排除决策）。不自动覆盖游戏、同步仓库、提交、推送或删除旧发布包。

安装或发布仅在当前任务包含这些动作时进行。安装前确认目标游戏仍对应本批次快照；基础汉化先安装，再安装本批次覆盖文件。`retired` 项是处理清单，不代表可以删除游戏目录中的同名文件；必须确认那是曾由本项目安装且已失效的文件。不要用全目录删除同步处理字体和用户自有文件。

验收和所需交付完成后：

```bash
python3 tools/batch.py finish
```

完整批次移动到 `archives/batch_<批次名>/`，基线推进至其目标快照，活动批次清空，重新等待更新。所需语义与游戏加载检查仍由人执行；工具无法证明自然语言翻译完全正确。

## 6.1 发布到发布仓库（仅在任务要求发布时做）

发布仓库：<https://github.com/haool871/limbus-zh-10ch>（本地目录 `../limbus-zh-10ch`）

它是**给玩家的仓库**，只放「要复制进游戏的东西」：
`patch/`（补丁本体）+ 安装 README + CHANGELOG + `publish.sh`。
术语库、流程文档、工具、审计说明都留在本知识库仓库，**不在发布仓库里重复一份**，
避免出现两份会各自漂移的快照。

```bash
cd ../limbus-zh-10ch
./publish.sh ../_kb/out/delivery_<批次名> v<版本>
# 确认清单无误 → 输入 y
git push origin main && git push origin v<版本>
# 然后在 CHANGELOG.md 追加一行并再提交
```

`publish.sh` 的安全约束（不要绕过）：
- **必须**来自 `batch.py export`（要求交付目录含 `delivery.json`）；手攒的目录直接拒绝
- 同步前打印新增/更新/移除清单并要求确认；只同步 `.json`
- **不自动 push**，推送留给人工确认
- 历史版本靠 **git tag** 保留，所以 `patch/` 始终等于最新一版的完整交付集，不会越积越乱

**`patch/` 与批次交付集的对应关系**：`patch/` ≡ 最近一次 `batch export` 的 `patch/` 内容。
不要手工往 `patch/` 加文件或改文件——会被下一次发布整体覆盖，而且绕过了批次验收。

**什么时候不要打 tag**：交付集为空时（零协已覆盖全部文本）不打 tag，
否则 Releases 里会出现一个空包。

## 7. 参考语料更新与历史工具

`pm_lib` 默认读取记录的基线，可用 `LIMBUS_SNAPSHOT=<快照路径>` 指定其他版本。缓存记录来源；重建不需要先删除索引。

```bash
python3 tools/pm_lib.py build
python3 tools/export_corpus.py
python3 tools/align_index.py build
```

重复/空 id 在导出中保留并标记歧义，不自动跨语言配对；嵌套文本保留真实路径。机器术语表仍须回查原始记录，不能仅凭主流频率裁定每个语境。

旧 TSV 写入器、`mk.sh`、旧 `lint_zh.py`/`check_consistency.py` 命令行已退役并明确报错，代码仅供历史复核。不要恢复旧 `patch_v2/` 或 `out/LLC_zh-CN/` 来运行它们。旧版完整流程和工具保存在上一轮归档中。
