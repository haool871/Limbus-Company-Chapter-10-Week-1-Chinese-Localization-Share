# 翻译流程 SOP（英文 → 中文）

面向「拿到 Limbus Company 新版本英文文本，产出零协会风格中文」的标准作业流程。
本文所有技术规则均由工作区语料实证得出，引用见文末。

---

## 0. 先决条件：术语与口吻的权威顺序

翻译任何句子前，判断顺序**必须**是：

```
① terms/术语表.md / terms/glossary.tsv   ← 专名、机制名的唯一权威
② 语料检索（零协会既有译法）              ← 同一概念的既有措辞
③ style/角色/*.md                        ← 说话人是谁 → 决定语域
④ style/叙事与旁白.md、战斗与机制文本.md、UI与系统文本.md  ← 文体
⑤ 自拟                                   ← 仅当前四步都无答案
```

**禁止**跳过 ①② 自创译名。游戏里同一专名会横跨 941 个剧情文件反复出现，一次不一致会显得很突出。

---

## 1. 接稿：确认输入形态

新文本通常是以下几种之一：

| 输入形态 | 处理方式 |
| --- | --- |
| 已解包的新 JSON（结构与 `Lang/LLC_zh-CN/**` 一致） | 直接对照 `en` 版本逐条译，保留 `id` 与字段名不动 |
| 只有英文原文片段（无 id） | 用 `grep` 在语料里定位对应文件与上下文，再译 |
| 官方新增文件（汉化包尚无该文件） | 以官方 `Assets/Resources_moved/Localize/en/` 下同名文件为基准；**这是当前 130 个未覆盖文件的正常补译来源** |

**文件对应关系**（重要）：
- 官方英文文件**带语言前缀**：`EN_MainUIText.json`、`StoryData/EN_1D101A.json`
- 汉化文件**不带前缀**：`MainUIText.json`、`StoryData/1D101A.json`
- 目录结构完全相同，**只去前缀**。

## 2. 检索既有译法（最耗时也最关键的一步）

```bash
cd /home/shb/文档/汉化/_kb

# 看某个文件的中/英/韩/日四语逐条对照（最常用）
python3 tools/pm_lib.py show MainUIText.json
python3 tools/pm_lib.py show StoryData/S709B.json

# 按关键字找文件
python3 tools/pm_lib.py find BattleKeywords

# 在中文语料搜词，确认既有译法（也可 -l en / -l kr）
python3 tools/pm_lib.py grep 事务所 -l cn

# 术语表（en → cn，带频次与来源）
grep -i "wing" terms/glossary_all.tsv
```

判断要点：
- 若术语表里有 → **必须**照用。
- 若术语表没有，但语料里能搜到既有译法 → 沿用既有译法（哪怕个人觉得有更好选择）；如确需改进，记入待议清单，不要单点改动。
- 若确实是全新概念 → 自拟后**登记进术语表**，保证后续一致。

## 3. 判定位次：谁在说、说什么文体

1. **对话**：查 `style/角色/<中文名>.md`，按该角色的语域、句长、口癖、称呼方式处理。
   说话人识别：剧情 JSON 里 `model`（韩文内部标识）是**稳定的说话人键**；`teller` 是显示名，常缺失。
   对应表见 `data/speaker_map.json`（韩文 model → 英文名/中文名）。
2. **旁白/场景**：走 `style/叙事与旁白.md`。
3. **技能/被动/状态/EGO/饰品**：走 `style/战斗与机制文本.md`，句式**必须**贴合既有模板。
4. **UI/系统/商店/通行证**：走 `style/UI与系统文本.md`。

## 4. 硬性技术规则（违反会导致显示或功能问题）

### 4.1 方括号标记：**必须区分两类** ❗
方括号里的内容有两种截然不同的性质，处理方式相反——这是最容易出错的地方。

**（a）引擎标签 = 拉丁标识符 → 原样保留，不翻译、不加空格**
`[Vibration]`、`[Combustion]`、`[Sinking]`、`[OnSucceedAttack]`、`[WhenUse]`、`[CantIdentify]`、`[VibrationDistribution]`、`[FusionVibration]` 等。

- 实测：661 个不同中文方括号标记中，**首尾带空格的为 0 个**。
- 实例：`使[Vibration]层数最高的1名人格的[Vibration]以[VibrationDistribution][FusionVibration]`
- 判别特征：内容是**无空格的拉丁字母/下划线标识符**（`^[A-Za-z_][A-Za-z0-9_]*$`）。

**（b）显示文本 = 人名/状态名/样式包裹 → 必须翻译**
| 英文 | 中文（官方） |
| --- | --- |
| `Trussed [Hong Lu]` | `捕缚[鸿璐]` |
| `Book of Vengeance [Heathcliff]` | `复仇账簿[希斯克利夫]` |
| `Bladetrail [Afterimage]` | `剑痕[残像]` |
| `The Middle - Vengeful Tattoo [<s>Great Sister</s>]` | `中指-仇怨纹身[<s>长姊</s>]` |

即：方括号里若是**专名**，翻成中文；若内部还包着 `<s>…</s>`/`<i>…</i>` 样式标签，标签本身保留、内部文字翻译。

- 全语料扫描：真正"方括号内容未译"的漏网仅 12 处（如 `[EP 1]`、`[Lacrimosa-Crescendo]`、`[2xPostLine]`），说明此规则在既有汉化中执行得非常严格。

**（c）样式标签 `<>` 允许删除**
`<i>…</i>`、`<s>…</s>` 这类在中文里常被整组删掉（官方 `DawnLight`、`Firstlight` 即如此）。**常见但非强制**；同一文件内保持一致即可。`<color=#xxxxxx>`、`<style="...">` 这类带参数的**必须保留**。

### 4.1b 自动质检
```bash
python3 tools/qa_check.py --official StoryData/S709B.json   # 用官方英文为基准
python3 tools/qa_check.py en.json cn.json                   # 或指定两个文件
```
会检查：id 覆盖、引擎标签、`{}` 占位符、未译/空译、长度异常。**语义仍需人工通读**。

### 4.2 占位符原样保留
`{0}` `{1}` `{num}` 等一律不动，只调整其外侧中文语序。

- 实例：`罪人[{0}]向那白光伸出手。`

### 4.3 标点（实测计数，**按体裁分化，不要一概而论**）
| 标点 | 全库实测 | 规则 |
| --- | --- | --- |
| 省略号 | `……` 32,694；`…` 65,538 | ⚠️**分体裁**：剧情/语音**几乎只用 `……`**（旁白 4878 vs 单…3；对话 26841 vs 35）；**机制/技能文本反而单 `…` 更多**（104 vs 53）。按你正在译的体裁选，同一文件内保持一致 |
| 破折号 | `——` 仅 179；英文 em dash 旁白 535 行 → 中文仅 40 行用 | **极少用**。打断语用「……」；其余转逗号/句号/重组句 |
| 引号 | 弯引号 `“”` 3,039；直角 `「」` **0** | **一律用 `“”`**（686k 行独立复核确认 `「」` 零出现） |
| 括号 | 全角 `（）` 223；半角 `()` 多为模板数据 | 正文用全角 `（）`；模板/枚举数据不动 |
| 编号 | `1)` 与 `1）` 并存（FAQ 内 4:1） | **同一篇内统一**，不要一律改全角 |
| 问号感叹号 | 中文用全角 `？！` | 与英文半角区分 |

### 4.3b 动作/音效标记（实测，`*动作*` 285 行 → 中文仅 9 行保留）
- **整行音效** → 拟声词：`*Wham! Wham! Wham!*` → `咚！咚！咚！`
- **需说明的声音** → 全角括号：`*Whistle*` → `（口哨声）`
- **行内强调** → **删除标记**，用词汇本身表达强调
- `<i>` 624 → 108（多用词汇表达强调）；`<color>` 293 → 293（**必须保留**）

### 4.4 空格
**关键词内联时有尾随半角空格**（易漏）：`流血 强度`（344 例，无空格 0 例）、`破裂 强度`（268/0）、`震颤 层数`（106/0）。
但 **`震颤引爆` 一类复合词不加空格**（161/0）。
其余中文与英文/数字混排**不加空格**（如 `LCCB的员工证`）；方括号标记与数字/中文之间也不加空格。

### 4.5 换行与分段
`AbEvents`、`AbnormalityGuides` 等长文本用 `\n` 分段。翻译时**保持与原英文一致的段落数**，便于对照与排版；文本框过窄时可拆分长句，但不要合并段落。

## 5. 句式规范：英文 → 中文的转换规律

### 5.1 机制描述：条件前置 + 「等同于……的数值」句式
英文是「效果 + 条件 + 时长」的松散语序，中文习惯**把时长/条件放前面**，并用固定短语收尾。

| English | 中文（官方） |
| --- | --- |
| `Attack skills gain final Power by the effect's Count for one turn.` | `一回合内攻击技能的最终威力增加等同于本效果层数的数值。` |
| `Speed increases by the effect's Count for one turn.` | `一回合内速度值增加等同于本效果层数的数值。` |
| `Defense skills gain final Power by the effect's Count for one turn.` | `一回合内守备技能的最终威力增加等同于本效果层数的数值。` |
| `Targets 2 or more foes.` | `同时攻击不低于2名敌方单位。` |

注意：中文比英文**长得多**（技能类均值 英文 12.7 词 → 中文 59.4 字），这是刻意的书面化，**不要为压缩字数而删掉条件或数值**。

### 5.2 名词优先，动作名词化
- `Apply X` → `施加X` / `使目标获得X`
- `On hit` → `命中时`
- `When using this skill` → `使用本技能时` / `本技能使用时`
- `raise Stagger Threshold` → `使混乱阈值**前移**`；`lower` → `**后移**`
- `N or more` → `不低于N`
- 乘号用全角 `×`（不是字母 `x`）
- `Only`（人格专属）→ `人格专属`

### 5.2b 技能/被动**名称**的长度规范（实测 2,987 个名字）
- 平均 **4.1 字**，中位数 **4 字** → 译名尽量控制在 4 字上下。
- 守备技能固定三类：**防御 / 闪避 / 反击**。
- 攻击类名称允许更自由，但仍以短促为佳。

### 5.2c 占位符的可能重排
272 行含占位符的文本中，**266 行序列与英文一致，6 行中文做了重排**（如 Vibration/Breath 的语序调整）；`+{0}0%` 这类**不可"修正"**，「罪人[{0}]」式共 4 处实证。改动占位符顺序前，务必先 `grep` 同文件既有做法。

### 5.3 被动转主动、去除冗余主语
英文被动句优先改主动；英文里重复的 `the target` 在中文里可承前省略，但**首次出现必须点明**。

### 5.4 长度基准（en 词 → 中文字，均值；用于自查异常）
| 类别 | 组数 | 均英词 | 均中字 | 字/词 |
| --- | --- | --- | --- | --- |
| 剧情 StoryData | 72,965 | 14.2 | 25.0 | 1.76 |
| 语音台词 | 5,231 | 17.2 | 28.1 | 1.64 |
| 事件 | 3,824 | 29.5 | 57.4 | 1.95 |
| UI | 3,345 | 19.6 | 36.7 | 1.88 |
| 机制/状态 | 5,859 | 19.9 | 46.0 | 2.31 |
| 技能/被动 | 23,568 | 12.7 | 59.4 | 4.66 |
| 歌词 | 479 | 6.1 | 15.6 | 2.56 |

译文长度明显偏离所属区间时，回头检查是否漏译/赘译。

### 5.5 不要保留英文语序痕迹
- 避免 `一个……的……的……` 长定语句堆叠；中文拆成短句。
- 英文的 `Well, ...` / `Look, ...` 类语气起手，按角色转为中文口癖（见各角色文风文件），不要一律译成「好吧，」「听着，」。

### 5.6 ❗从英文转译最大的系统性陷阱：**英文丢敬称，中文必须补回**

零协会汉化是**跟随韩文原文**做的，而官方英文版**系统性地丢弃韩文敬称**（씨 / 님）。若你直接照英文译，会**成批丢失人物关系与礼貌层级**——这是本项目最大的坑。

实测（以韩文 kr 侧带敬称为基准）：

| 角色 | 韩文带敬称行数 | 英文版丢失 | 中文汉化保留 |
| --- | ---: | ---: | ---: |
| 以实玛利 | 205 | 140 行（**68%**） | 146 行（71%） |
| 辛克莱 | 247 | 153 行（**62%**） | 207 行（**84%**） |
| 希斯克利夫 | 46 | — | 23 行（且多为反讽用法） |

**操作规则**：只凭英文翻译时，必须根据「**被称呼者是谁**」主动补回「先生 / 小姐 / 女士 / 经理」等敬称：
- 对但丁（上司）→ 敬称 + 「您」
- 对同僚中生代/前辈 → 「〇〇先生」「〇〇女士」
- 辛克莱对**德米安**是唯一的**无敬称**例外（直呼其名），不可加敬称
- 希斯克利夫对但丁的固定称呼是「**钟表头**」（38 次），不是「经理」

**陷阱**：韩文 `씨` 多数时候是敬称，但在希斯克利夫口中大量是脏话 `아이씨 / 야이씨`，不是敬称——用正则统计时必须排除。

**陷阱 2（与 §5.9 的分界，别搞反）**：韩文敬称后缀**不是都要补**——

| 后缀 | 性质 | 中文处理 |
| --- | --- | --- |
| `씨` / `님` / `양` | **敬称**（表尊重） | **必须补**：先生／小姐／女士／经理／大人 |
| `군` | **小称**（表对方年少/后辈） | **丢掉不译**（同 en `young X`）：`이스마엘군` → 以实玛利，不写「年轻的以实玛利」 |

一句话记法：**表尊敬的要补，表"你比我小"的不要补**。详见 §5.9。

### 5.7 口吃与迟疑的分工（以辛克莱为典型）
英文用连字符表现口吃（`W-wait`、`I-I`），中文有**两套不同手段，不可互换**：
- **顿号「、」承担音节口吃**：`等、等一下`、`经、经理`
- **省略号「……」承担语尾中断/迟疑**：`我不想让你们看到……`

| --- | --- | --- |

| 以实玛利 / 辛克莱 → 但丁 | **经理** / **但丁经理** + 您 | — |
| 堂吉诃德 → 但丁 | **经理老爷**（kr 관리자 나리） | 与她的「老爷」体系一致 |

### 5.9 人称与自称体系（按角色严格区分，不要互相污染）

> **权威口径**：零协基础包（`LimbusLocalize_latest`）按 `model` 统计的**实际自称分布**。
> 复核命令：`python3 tools/check_speech_context.py --table`

| 角色 | 零协实际自称分布（出现该词的句数 / 总句数） | 称人 |
| --- | --- | --- |
| 李箱 | 我×473、我们×92、本人×4；**「吾/汝」0 次** | 书面语，不用汝/吾 |
| 堂吉诃德 | **吾×579、吾等×134**；我×22、本人×2、在下×2、我们×1 | **汝**（253 次）；thou 不机械对译（英文 321 行 → 中文 230 行，约 72%） |
| 浮士德 | **第三人称自称「浮士德」168 句**（EN 189 句，保留率 89%）；我×550、我们×267 | 对同伴加先生/小姐 |
| 以实玛利 | 我×749、我们×301、咱×11 | — |
| 奥提斯 | 我×527、我们×240、本人×3、在下×1 | — |
| 希斯克利夫 | 我×694、我们×178、在下×1、咱×1、吾×1 | — |
| 鸿璐 | 我×665、我们×130、在下×1、本人×1 | — |
| 辛克莱 | 我×623、我们×168、本人×1 | 口吃/迟疑见 §5.7 |
| 罗佳 | 我×567、我们×199、咱×5 | — |
| 格里高尔 | 我×552、我们×210、咱×4 | — |
| 良秀 | 我×359、我们×24 | 极简、命令式 |
| 默尔索 | 我×216、我们×53 | 平板陈述 |
| 但丁 | 我×622、我们×227、本人×1 | 内心独白用 `<>` |

**读表要点**

- **「我／我们」是包容性复数**，任何角色都会自然使用（「我们前面的」「我们的规则」），**不能**因为某角色「我们」少就报错。
- 真正**独占性**的自称是「吾／吾等／本人／在下／咱／俺」，一个角色要么一律用、要么基本不用。判据取最严谨形式：**只在该词于零协语料中对这个角色出现 0 次时才告警**（见自动质检）。
- 「本人」是零协的**罕见但合法**自称（奥提斯×3、李箱×4、但丁×1 等），不要当成错误统一改掉。

**⚠️ 自称占优势的角色不要被「通顺」带偏**：堂吉诃德以「吾」为绝对主格（吾 579 : 我 22 ≈ 26:1）。
新译她的台词时若写成「我／我们／本人」，就是换了一个人——**必须用「吾／吾等」**。

**特别提醒（不要"修正"官方刻意设计）**：Canto VII 真相场景中，官方**故意**让堂吉诃德从「吾/汝」掉回「我/你」，并保留「吾会……我会去的」这种改口痕迹——这是演出效果，翻译时必须保留，不可统一。

**`young + 名字` / KR `X 군` 的固定处理**：零协语料中 `young + 名字` 实例 **100% 丢掉不译**（`young Hong Lu`→鸿璐、`young Ishmael`→以实玛利、`young Xichun`→惜春、`young Faust`→浮士德）。**不要译成「年轻的××」或「小朋友」**。基础包堂吉诃德台词里 KR 含「군」的实例为 0，故「군」同样按此规律处理。

### 5.9b ❗批量翻译最容易踩的一类坑：**字段／列错位**

新文件的记录里除了 `content` 还有 `teller`、`title`、`place`、`nickName`、`desc` 等字段。
批量处理（正则替换、累加、把某句套用到整个文件）时**误伤这些列**，会造成极难发现、但游戏内一眼可见的错误。

**实战事故**：`StoryData/P10416.json` / `P10816.json` 的 `title` 列（店铺名／身份）被整体写成同一个值——
53 条记录的 `title` 全变成「Le Noir鞋履馆」；正确应是店家名与 `顾客`／`异邦人`／`？？？` 并存（英文源共 4 种取值）。

**正确做法**：

1. **逐条（per-id）对齐，不要全局取众数**。判据是「同一个 `id` 在英文源里是什么」，不是「这个英文词在整个语料里最常见什么」。
   ```bash
   # 先看清英文源每个 id 的该字段取值分布
   python3 - <<'EOF'
   import json, collections
   d=json.load(open('EN_P10416.json',encoding='utf-8-sig'))['dataList']
   print(collections.Counter(str(r.get('title')) for r in d if r.get('title')))
   EOF
   ```
2. **改完必须核对「取值种类数」是否与英文源一致**：
   ```bash
   # 英文 N 种 title → 中文也应 N 种；少于 N 种就说明被压平了
   ```
3. **只改该改的那个字段**，改完 diff 一次，确认变化只落在预期字段上（见 §7.4）。

同类风险字段：`teller`（显示名，可本地化）、`title`、`place`、`nickName`、`desc`（有时是韩文开发备注，见 `*.tsv.skip`）。

### 5.9c ❗补译缺口文件时，**不要从骨架重建**

「骨架重建」（照英文源重建结构 + 回填译文）适合**全新文件**，但对已有译文值的文件会**清空译文**。

**实战事故**：`MainUIText-a1c10p1.*` 的译文被骨架重建覆盖。

**正确做法**：从**现存文件**里把译文抽成 `{id: {字段: 译文}}` 保存下来，重建后按 id 重新灌回；灌回后校验值非空且数量一致。
`tools/` 下已有 `fill_gaps.py`、`apply_gap_patch.py`、`rebuild_skeleton.py`、`coalesce_parts.py` 可参考，但**灌回后的核对不能省**。

### 5.10 ⚠️ 语料陷阱：model 归属 ≠ 说话人
`StoryData/E001X.json` 是**身体互换**的喜剧章：该文件里 `model` 字段标的是**身体**而非真正的说话人（`파우스트` 行实际是堂吉诃德语气，`돈키호테` 行实际是浮士德语气）。
类似地，镜像/记录体场景（如 `S202A`、`S521B`、`E904B`）里李箱会用「本人」（kr 본인）自称，与主线的「我」不同层。

**结论**：拿语料学习口吻时，若某文件出现明显的"串味"，先怀疑是特殊设定的章节，不要盲信 `model`。

> **注意与 §5.9 的关系**：§5.9 的自称分布表是**全量统计**，已把这些特殊章节的用例算进去（例如李箱的「本人×4」就来自镜像／记录体场景）。
> 也就是说：**表里的少数派写法往往正是"特殊场景合法用法"的信号**，不要在普通场景里照抄。
> 自动化工具 `check_speech_context.py` 只在某写法对该角色**全语料 0 次**时才告警，正是为了不误伤这类少数派。

### 5.11 ❗官方还没出英文时：以**韩文原文**为源，但目标语域仍按零协中文

Canto 10 这类最新内容，官方常出现「**韩文已放、英文/中文栏还是空占位**」的状态
（实测 `StoryData/S1001B`~`S1005B`：kr 有正文，en 与 cn 的 `content` 全为空）。

此时流程要改：

| 步骤 | 做法 |
| --- | --- |
| 源文本 | 用 **kr `KR_*.json`** 为源（不是空的 en） |
| 目标语域 | **仍以零协中文既有习惯为准**，而不是「韩文是什么语域就直译什么语域」 |
| 人称／自称 | 逐条跑 `tools/check_speech_context.py`，确保不引入该角色从未用过的写法 |
| 术语 | 仍查 `terms/` 与零协语料；韩文新词若零协没译过，才自拟并登记 |

**为什么不能照韩文语域直译**：韩文的 `본인`（本人）是**中性第一人称**，可以在正式表述里随便用；
但零协给堂吉诃德定的是「**吾**」（吾 579 : 我 22），给她写「本人」就是换了一个人。
**源语言决定"说什么"，零协语料决定"怎么说"**——这两件事必须分开。

**还有一条**：kr 与 en 有时**对不上**（同一 id 两边内容不一致，说明是不同修订批次）。
发现不一致时，**不要猜**，直接在交付说明里标出来交人工决策。

### 5.12 ❗别用脚本对 JSON 做文本级清洗

**实战事故**：一个"清理脚本"用正则处理 E.G.O 标题，**删掉了换行并留下孤立的 `</size>`**，
破坏了美术/样式标记（正是你最该保住的东西）。

**规则**：

1. 要改 JSON，就走 §7.0 的**译文表 → 合并**流水线，或**逐字段精确赋值**；
2. **绝不**对 JSON 全文跑「替换／删空白／删标签」类正则；
3. 动手前先**备份**（`cp` 到 `/tmp/..._backup`），改完**逐条 diff**，确认变化只落在预期字段；
4. 一旦发现标记被破坏：**不要试图原地修补**——从已知良好的副本恢复（如仓库里的 `patch/`），再只重放那一个真正的改动。

## 7. 交付与更新

### 7.0 已实现的工程化流水线（推荐）
不要手写 JSON——用「译文表 + 脚本合并」，可从结构上保证美术标记不被改坏：

```bash
cd /home/shb/文档/汉化/_kb

# 1) 生成译文表骨架（含嵌套路径；自动跳过 id 等非文本字段）
python3 tools/make_tr_template.py StoryData/S1002B.json
#    → translate/StoryData__S1002B.tsv   （第三列填中文，\n 表示换行）

# 2) 合并生成中文 JSON（结构/键序完全照抄英文源，只替换译文）
python3 tools/build_translation.py StoryData/S1002B.json translate/StoryData__S1002B.tsv
#    → out/LLC_zh-CN/StoryData/S1002B.json
#    必须看到 ✅「标记校验全部通过」；❌ 表示颜色/引擎标签/占位符不一致，必须修

# 3) 成品验证（对比英文源逐字段：结构、id 序列、标记、占位符、译出率）
python3 tools/verify_output.py                    # 全部
python3 tools/verify_output.py MainUIText-a1c10p1.json
```

要点：
- 合并脚本**只改第三列对应的字段**，未提供译文的字段保留英文（宁可漏译，不破坏）；
- 会打印「⚠ 未译 N 条」帮助查漏；
- `*.tsv.skip` 可列出不翻译的字段（如 `BattleSpeechBubbleDlg` 的 `desc` 是韩文开发备注）；
- 嵌套结构（`levelList[0].desc`、`texts[1]`）已支持。

### 7.1 常规交付
1. 译文写回与英文同名的 JSON（**去掉语言前缀**），放入 `Lang/LLC_zh-CN/` 对应目录。
2. 若是整包更新，`Info/version.json` 的 `version` 需递增（格式 `YYYYMMDD` + 序号，如 `2026090501`），供工具箱比对。
3. 新增/修订的术语，同步更新 `terms/术语表.md`。
4. 验证：把改动的文件用 `python3 tools/pm_lib.py show <文件名>` 再跑一次，顺读检查。

### 7.2 补丁包的**范围**必须明确（极易漏文件）

补丁有两种性质的文件，**数量要分别核对**，否则会漏发：

| 类型 | 含义 | 漏了会怎样 |
| --- | --- | --- |
| **新增文件** | 零协基础包里**没有**的文件 | 整个模块（如整章剧情/整个 `RPGSystem`）在游戏里**不存在** |
| **覆盖文件** | 基础包里**有**、需要改写部分字段的文件 | 只有新增内容缺字，老内容正常 |

**实战事故**：第一版补丁只打包了 25 个"覆盖文件"，漏掉了 **104 个全新文件** → `RPGSystem`（44 个）与 `StoryData`（21 个）整块缺失。

**发布前必跑**：
```bash
# ① 数量对得上
find patch -type f | wc -l                      # 应等于「新增 + 覆盖」

# ② 新增文件真的进包了（拿基础包做差集）
comm -23 <(cd patch && find . -type f | sort) \
         <(cd "$BASE_PACK" && find . -type f | sort) | wc -l

# ③ 覆盖文件没有把零协原文改坏（见 §7.3 一致性校验）
```

### 7.3 一致性校验三层（从强到弱，都要跑）

```bash
cd /home/shb/文档/汉化/_kb
```

1. **与零协基础包共享字段 → 差异必须为 0**
   补丁**绝不能改动零协已翻好的原文**。做法：对每个「补丁与基础包都有」的文件，逐 `id` 逐字段比对，仅统计**两边都存在的字符串字段**。
   ```
   16769 个共享字段，差异 0   ← 合格
   ```
2. **反向术语校验（最强证据）**：把基础包当词典，用**官方 en** 做键，建「英文原文 → 零协译文」映射（实测 93,480 条），
   然后扫补丁每个文件：**同一句英文，补丁译文是否与零协一致**。
   ```
   同英文句、零协译法不同: 0   ← 合格
   ```
   这一条能一次性抓出「零协翻过的词我自创了译法」。
3. **零协既有术语扫描**：`python3 tools/check_established_terms.py`（会报 200+ 条，**其中大量是英文子串误报**，需人工过）。

### 7.4 改动落地与验收（每次改完都走一遍）

```bash
# 1) 结构完整性：键集合 / 记录数 / id 序列 必须与官方 en（或 kr）逐一对齐
#    —— 用备份对照，确认变化只落在预期字段（不要只看"文件能解析"）
# 2) 禁用语复查：把本次要清除的写法在目标角色的全部台词里 grep 一遍，须为 0
# 3) 合法性：所有打包文件 json.load 无异常
# 4) 覆盖到游戏后 diff：补丁目录 vs 游戏目录，除"仅游戏侧存在的基础包文件"外差异必须为 0
```

**踩过的具体坑（都靠上面流程抓出来）**：

| 坑 | 症状 | 根因 |
| --- | --- | --- |
| `build_translation.py` 的 `STRICT_TAG` 用了 `re.I` | 但丁的**内心独白** `<I …>` 被当成斜体 `<i>`，239 处误判 | 大小写不敏感导致「引擎标记」与「样式标记」混淆。**修法：去掉 `re.I`，只匹配自闭合／带 `=` 属性的标签** |
| 批量替换造出 `黄金皮毛毛` | 叠字 | 替换未锚定词边界；韩文 `황금가죽` 只对应「黄金皮革」 |
| `Desperation` 译「拼命」 | 与零协不一致 | 零协是「**迫切**」（`Passives.json` 1070721/1070731）；**先查再译** |
| `SisyphusAmber` 被词典带偏成「怠惰」 | 词不达意 | sin 属性 `Amber`＝怠惰是**另一回事**；这里 `Amber`＝**琥珀** |
| 同一英文词在不同文件被译成不同中文 | 术语漂移 | 机械词典查表；**必须逐条对齐官方 en 的同一 id** |
